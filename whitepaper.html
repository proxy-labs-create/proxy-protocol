Abstract

Infrastructure for autonomous AI agent payments now exists. x402, Agentic Wallets, and ERC-8004 have been deployed at scale. But every major solution is Coinbase-controlled, KYT-screened, and stablecoin-denominated. For agents that need to operate without identity exposure, without a corporate gatekeeper, and without a settlement currency that can be frozen — none of it works.

PROXY is the permissionless alternative. It enables autonomous AI agents to hold, spend, and settle $PROXY — a native token with no issuer and no compliance layer — anonymously on Base. No KYC. No KYT screening. No admin keys. No entity that can freeze a balance or block a transaction. PROXY is built on Base, launched as a fully fair-launch token, and governed entirely by its holders.

Agent payments exist.
But Coinbase controls them.

The infrastructure for autonomous AI agent payments has arrived. x402 — Coinbase's open payment protocol — has processed over 165 million transactions. Agentic Wallets provide non-custodial agent wallet infrastructure on Base. BNB Chain has deployed ERC-8004 for agent identity. The problem is no longer that agent payments don't exist. The problem is who controls them.

Every existing solution settles in USDC and routes through corporate infrastructure. No permissionless, anonymous alternative exists. Until PROXY.

The four structural problems with existing agent payment infrastructure are not technical — they are political and architectural:

1.1 — Corporate Control of the Rails

x402 is Coinbase's protocol. The x402 Foundation is co-governed by Coinbase and Cloudflare. Coinbase's Agentic Wallets include built-in KYT (Know Your Transaction) screening that cannot be disabled. Infrastructure controlled by a single corporation — however well-intentioned — is not permissionless infrastructure. It can be updated, restricted, or shut down at corporate discretion.

1.2 — Stablecoin Settlement is Not Censorship-Resistant

Every major agent payment solution settles in USDC. USDC is issued by Circle, which operates under US regulatory jurisdiction and can freeze balances, blacklist addresses, and comply with law enforcement requests. An agent payment network that settles in a regulatorily-compliant stablecoin inherits all the censorship properties of that stablecoin — regardless of how decentralised the routing layer is.

1.3 — KYT Screening Creates a Surveillance Layer

Coinbase's Agentic Wallets include compliance-ready KYT screening that automatically blocks high-risk interactions. This means every agent transaction is evaluated against Coinbase's risk model. For agents operating on behalf of individuals or institutions where transaction privacy is a requirement — not a preference — this is an architectural incompatibility, not a configuration option.

1.4 — There Is an Off Switch

Any infrastructure operated by a corporate entity has a corporate kill switch. Coinbase can update x402, restrict Agentic Wallet functionality, or comply with regulatory orders that affect the network. The promise of autonomous, unstoppable agent commerce cannot be built on infrastructure that can be stopped.

03 — How PROXY Works

Five steps.
Zero humans.

The PROXY protocol reduces every agent resource transaction to a five-step atomic flow. Each step is designed to be trustless — neither party is required to identify themselves, and payment is only released upon cryptographic proof of delivery. The entire cycle operates at machine speed.

01
Agent Wallet Initialisation
An autonomous agent is deployed with a PROXY wallet — a non-custodial, on-chain identity on Base funded in $PROXY by its operator at initialisation. Post-funding, no human interaction is required. The agent controls its own wallet, manages its own budget, and initiates all transactions autonomously. The wallet address is the agent's sole identity on the network — no name, no email, no KYC.
02
Resource Request Broadcast
When the agent requires a resource, it constructs a signed request specifying the resource type, required parameters, maximum acceptable latency, and a budget ceiling in $PROXY. This request is broadcast to the PROXY routing layer via a standardised AgentRequest schema. The budget ceiling is atomically escrowed in the PROXY smart contract at broadcast, guaranteeing payment availability to providers.
03
Anonymous Routing
PROXY's routing layer matches the request to an eligible provider using a weighted matching algorithm evaluating provider stake weight, latency record, and resource availability. This matching is performed without either party revealing their identity. Zero-knowledge attestations confirm provider eligibility without exposing wallet addresses or operational details.
04
Delivery and Proof Submission
The provider fulfils the resource request and submits a cryptographic DeliveryProof to the PROXY proof layer. For inference jobs, the proof includes a deterministic hash of the output against committed model weights. For data feeds, the proof includes a signed timestamp and source attestation. The proof layer validates the submission before any escrow is released.
05
Instant Settlement
Upon successful proof validation, the PROXY escrow contract releases the agreed $PROXY amount to the provider's wallet on Base. Settlement is instant — finalised within the Base block time of approximately two seconds. The agent receives its resource. The provider receives its payment. The transaction is immutably recorded on-chain. No human was involved at any stage.

On anonymity throughout the flow: At no point does either the agent or the provider expose a human identity. The agent wallet is a pseudonymous on-chain address. Routing is performed via anonymous matching. Proof submission reveals only the job parameters, not the operator. This is not a privacy feature — it is the default state of the protocol.

4.1 — Pricing Mechanism

Resource pricing is set by providers at registration and updated dynamically based on demand signals. The protocol provides a standardised price discovery mechanism where agents submit requests with a maximum budget and providers compete on price and quality.

4.2 — Provider Registration

Providers register by bonding a minimum amount of $PROXY as collateral — subject to slashing in the event of failed delivery proofs or sustained downtime. Bonded $PROXY is locked from circulating supply for the duration of active registration.

5.1 — Agent Wallet SDK

A lightweight library enabling any AI agent framework to initialise and operate a PROXY wallet. It abstracts key management, request construction, and proof handling into a simple API surface — compatible with LangChain, AutoGPT, custom agent implementations, and any system capable of executing signed transactions.

5.2 — Routing and Anonymous Matching

The routing layer receives broadcast AgentRequest objects and executes a matching algorithm against the registered provider set. The matching process uses zero-knowledge proofs to verify provider eligibility without requiring providers to expose wallet addresses or operational details to the requesting agent.

5.3 — Escrow Smart Contracts

All payment flows through PROXY's escrow smart contracts deployed on Base. At request broadcast, the agent's budget ceiling is atomically locked in escrow. Failed or disputed proofs enter a 300-second dispute window, after which unresolved disputes are arbitrated by the on-chain governance mechanism. Contracts are non-upgradeable post-audit to eliminate admin key risk.

5.4 — Proof Layer

Every resource delivery must be accompanied by a DeliveryProof validated before any settlement occurs. Proof standards are resource-specific and published in the protocol specification. Providers that submit invalid proofs face immediate partial slashing of their bonded $PROXY collateral.

6.1 — Token Utility

Resource Payment — The Only Currency. All marketplace transactions are settled exclusively in $PROXY. Every inference job, data feed purchase, API call, and storage allocation consumes $PROXY from the agent's wallet. As agent adoption scales, so does the volume of $PROXY consumed — creating compounding demand pressure with no ceiling and no alternative payment path.

Provider Bonding. Providers bond $PROXY to register nodes on the network. This bond acts as collateral against delivery failures and locks supply from circulation. The more providers join, the more $PROXY is bonded and removed from tradeable supply.

Staking and Job Priority. Providers stake additional $PROXY above their minimum bond to increase their weighting in the routing algorithm. Higher stake weight means a higher share of incoming job allocations.

Governance. $PROXY holders govern the protocol through an on-chain DAO covering resource category additions, proof standard updates, fee parameters, dispute resolution rules, and treasury allocation.

6.2 — Supply Dynamics

The combination of mandatory payment currency status and provider bonding creates a dual-sided supply compression mechanism. Demand side: every agent transaction moves $PROXY from agent to provider — continuous velocity. Supply side: every active provider has bonded $PROXY locked from circulation. As both agent count and provider count grow, available circulating supply contracts while transaction volume expands.

07 — Anonymity Architecture

Anonymous
by default.

Anonymity in PROXY is not a feature that users opt into — it is the default state of every transaction. Neither agents nor providers are required to reveal any identity information at any point in the transaction lifecycle. This is enforced at the protocol level through three mechanisms: pseudonymous wallet addressing, zero-knowledge routing attestations, and anonymised proof submission.

For agents, this means that an AI system operating on behalf of an individual or institution can procure resources without exposing who controls the agent, what task it is executing, or what data it is accessing. For providers, it means resource supply can be offered without revealing operational infrastructure, geographic location, or business identity.

The protocol records only what is necessary for settlement — the transaction amount, the proof hash, and the block timestamp. Nothing more is required. Nothing more is stored.
